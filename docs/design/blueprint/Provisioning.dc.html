Provisioning als Code und Grafana-Import (M7, 0.7.4)

Dashboards, Datenquellen, Rollen und Alert-Regeln liegen als Dateien in Git und werden mit der Kommandozeile kalzit provision geprüft, angewendet und exportiert. In der Oberfläche sind sie dann schreibgeschützt und zeigen, woher sie kommen; Verwaltung > Provisioning zeigt Anwendungen, Fehler und Abweichungen. Dazu der Import von Grafana-Dashboards mit einem ehrlichen Bericht, was übernommen, angenähert oder weggelassen wird. Vom Inhaber freigegeben am 14.11.2026; Einzelheiten in docs/PLAN.md, Abschnitt 12, „0.7.4“.

1

Dateien im Repository

Ein Satz ist ein Ordner im Git-Repository: eine Datei kalzit-provision.yaml und je Ressource eine Datei in YAML oder JSON. Geheimnisse stehen nur als Verweis in der Datei, nie als Wert.

kalzit-config main

kalzit-config/ ├─ kalzit-provision.yaml ├─ datasources/ │ ├─ lager-pg.yaml │ └─ prometheus-prod.yaml ├─ dashboards/ │ ├─ vertrieb/ │ │ ├─ verkauf-ueberblick.yaml │ │ └─ wochenbericht.json │ └─ lager/ │ └─ bestand.yaml ├─ roles/ │ └─ lager-leser.yaml └─ alerts/ ├─ lager-kritisch.yaml └─ api-latenz.yaml

Eine Ressource je Datei. Der Dateiname ist frei; zählt, ist metadata.uid. Unterordner sind nur Ordnung im Repository.

ArtenProvisioningSet, DataSource, Dashboard, Role, AlertRule. Kontaktpunkte und Richtlinien folgen in einem späteren Schritt.
KALZIT-PROVISION.YAML 
apiVersion: kalzit/v1
kind: ProvisioningSet
metadata:
  name: kalzit-config
spec:
  organization: mousewerk
  # Nur in diesen Ordnern legt der Satz Dashboards
  # und Alert-Regeln an.
  folders: [Vertrieb, Lager]
  prune: false   # Entfernen nur mit --prune
DATASOURCES/LAGER-PG.YAML 
apiVersion: kalzit/v1
kind: DataSource
metadata:
  uid: lager-pg
  name: Lager PG
spec:
  type: postgresql
  host: db-lager.mousewerk.test:5432
  database: lager
  user: kalzit_read
  password:
    fromEnv: KALZIT_PG_LAGER_PASSWORD
  readOnly: true
  pool: { max: 20 }
ALERTS/LAGER-KRITISCH.YAML 
apiVersion: kalzit/v1
kind: AlertRule
metadata:
  uid: lager-kritisch
  name: Lager kritisch
  folder: Lager
spec:
  query:
    datasource: lager-pg
    sql: |
      SELECT sku, menge FROM bestand
      WHERE lager = 'Nord'
  reduce: { field: menge, by: last }
  condition: { op: "<", value: 40 }
  for: 5m
  labels: { team: lager, schwere: kritisch }
  route: policies
Geheimnisse als Verweis
fromEnv
Umgebungsvariable dort, wo kalzit läuft (CI, Rechner)
fromFile
Datei, etwa ein eingehängtes Geheimnis im Container
fromStore
ein schon in Kalzit gespeichertes Geheimnis, mit Namen

Ein Wert im Klartext ist ein Fehler, schon bei plan. Kalzit verschlüsselt den Wert nach dem Anwenden in seinem eigenen Speicher.

Fehler, Grenzfälle und leere Zustände

Meldungen in einfachen Worten mit dem nächsten Schritt: kaputtes JSON, keine Dashboard-Datei, Bibliothekspanels, fehlendes Recht, und die Seite Provisioning, solange es keinen Satz gibt.

JSON einfügen, Fehler

Das ist kein Dashboard. Die Datei beschreibt eine Datenquelle. Importieren kannst du hier nur Dashboards.

Bibliothekspanels, Rechte, alte Dateien

2 Bibliothekspanels fehlen in der Datei. Sie stehen nur als Verweis darin. Exportiere das Dashboard mit eingebetteten Panels, oder importiere ohne sie: sie landen als „weggelassen“ im Bericht.
Schema 14 ist alt. Kalzit liest es, nähert aber mehr an. Prüf den Bericht genauer.
Du darfst in „Lager“ keine Dashboards anlegen. Wähl einen Ordner, in dem du dashboards:write hast, oder frag eine Admin.

Provisioning, noch kein Satz

Noch nichts aus Dateien

Leg Dashboards, Datenquellen, Rollen und Alert-Regeln als Dateien in Git ab und wende sie mit der Kommandozeile an. Der leichteste Anfang ist ein Export dessen, was schon da ist.

kalzit provision export --folder Lager --out ./kalzit-config
kalzit provision plan ./kalzit-config
Anleitung lesen
Tipp: Lass plan --exit-code bei jedem Pull Request laufen. So siehst du Änderungen im Review, bevor sie jemand anwendet.

Dienstkonto für CI

Verwaltung > Dienstkonten: Konto „ci-provisioning“ mit der Rolle „Provisioning Lager und Vertrieb“ (provisioning:write, dashboards:write in Lager und Vertrieb, datasources:write, roles:write, alerts:write). Token mit Ablauf, nur als Hash gespeichert.

Jede Anwendung prüft die Rechte auf dem Server für jede Ressource, wie bei jeder anderen Anfrage. Ein Satz kann nie mehr, als sein Konto darf.
Rollen aus Dateien können keine Rechte vergeben, die das anwendende Konto selbst nicht hat.

Hinweise

Neu, Barrierefreiheit, Entscheidungen des Inhabers.

Neu

  • Provisioning als Code: Datenquellen, Dashboards, Rollen und Alert-Regeln als YAML- oder JSON-Dateien in Git, angewendet mit kalzit provision plan|apply|export.
  • Geheimnisse nur als Verweis (fromEnv, fromFile, fromStore); Klartext ist ein Fehler.
  • Verwaltete Ressourcen sind in der Oberfläche schreibgeschützt und zeigen Satz, Datei, Anwendung und Commit.
  • Verwaltung > Provisioning mit Anwendungen, Fehlern und Abweichungen; neue Rechte provisioning:read und provisioning:write.
  • Grafana-Dashboard importieren in vier Schritten (Datei, Datenquellen, Bericht, Fertig) und als kalzit provision import-grafana.

Barrierefreiheit

  • Die Plan-Ausgabe trägt die Bedeutung in den Zeichen + ~ - ! x, nicht in der Farbe; ohne Terminal-Farben bleibt sie lesbar.
  • Gesperrte Felder sind aria-readonly mit dem Grund als Text; „Bearbeiten“ ist disabled mit aria-describedby auf den Hinweis.
  • „Aus Dateien verwaltet“ ist ein Knopf mit aria-expanded; das Feld schließt mit Escape und gibt den Fokus zurück.
  • Die Schritte des Imports sind eine Liste mit aria-current=step; erledigte Schritte sagen „erledigt“.
  • „Sperre lösen“ fragt in einem alertdialog nach; Fokus startet auf „Abbrechen“.
  • Fokus nur bei :focus-visible, neutral; Auswahl mit leiser Fläche, keine Akzentfarbe.

Entschieden (14.11.2026)

  • Die Kommandozeile spricht mit dem laufenden Server über seine API und ein Dienstkonto-Token; Dateien kommen nur so auf den Server, er liest beim Start keinen Ordner.
  • Ein Satz gehört zu genau einer Organisation und besitzt seine Ordner; zwei Sätze dürfen dieselbe Ressource nicht verwalten.
  • apply ist alles oder nichts in einer Transaktion; Entfernen nur mit --prune, sonst bleibt eine Ressource ohne Datei schreibgeschützt stehen.
  • Verwaltete Ressourcen sind in der Oberfläche gesperrt; Organisations-Admins können im Notfall die Sperre lösen, das nächste apply überschreibt.
  • Teilen, Anmerkungen, Berichte, Stummschaltungen und Mitglieder einer Rolle gehören nicht in die Dateien.
  • Kontaktpunkte und Richtlinien kommen nicht in 0.7.4 in die Dateien.
  • Die Ausgabe der Kommandozeile folgt der Sprache des Systems (Deutsch oder Englisch, sonst Englisch); --output json hat englische Felder.
  • Neue Rechte provisioning:read und provisioning:write, nur für Organisations-Admins vorgegeben; Verwaltung > Provisioning steht in der Organisation, nicht beim Server.
  • Grafana-Import: nur Dashboards, keine Alarme, Quellen oder Plugins; der Bericht bleibt am Dashboard; weggelassene Panels werden nicht als Platzhalter angelegt.
  • Ein fehlgeschlagener Verbindungstest nach apply ist nur eine Warnung, kein Abbruch.
